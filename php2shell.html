PHP2Shell, one request at a time

Two critical PHP bugs, explained step by step. Scroll down and the line follows you from first request to final patch.

1

What is PHP2Shell?

PHP2Shell is the nickname for two critical bugs in PHP itself. An attacker can send a web request to an unpatched server and run commands on it, with no login.

CISA has listed both as exploited in the wild since October 26.

CVE-2026-109618

Memory corruption when PHP runs out of memory during a request.

NVD recordPHP advisory

CVE-2026-109619

A use-after-free: leftover memory from one request is reused by the next.

Is your PHP version fixed?

Type the version from php -v. The check runs in your browser and sends nothing anywhere.

Fixed releases per branch:

BranchFirst fixed version
PHP 8.58.5.12
PHP 8.48.4.27
PHP 8.38.3.36
PHP 8.28.2.35
Waiting for a versionTry 8.4.26 or 8.4.27.

Two traps. Linux distributions often fix PHP without changing the version number (Ubuntu 24.04 still reports 8.3.6 after its fix), so check your distribution's advisory. And the new version only counts once PHP has been fully restarted. Many servers also run several copies of PHP, and php -v shows only the command-line one. A fixed version also does not cover CVE-2026-115560, so keep session upload progress off.

4

What to do about it

  1. Find every copy of PHP

    Check php -v and php-fpm -v, then look for copies installed by a hosting panel, a container or a vendor appliance. Firewalls, VPN gateways and NAS boxes often run PHP in their management page, and you cannot patch that PHP yourself, so check each vendor's advisory.

  2. Update to the fixed release

    Move to 8.5.12, 8.4.27, 8.3.36 or 8.2.35, or install your distribution's patched package. PHP 8.1 and older get no official release, so use a vendor backport or upgrade.

  3. Restart PHP fully

    Restart PHP-FPM and the web server so the new version actually loads. Confirm which version the web server runs, not just the command line.

  4. Look back to October 17

    The first attempt on Amazon's honeypots was four days before the patch, so check logs and web folders from that date. Turning off session.upload_progress.enabled reduces exposure to one of the two bugs, but patching is the only real fix.

  5. Close the second door

    The firewall attacks paired PHP2Shell with a Linux kernel bug to turn web-user access into root, so patch the kernel too. Also take management interfaces off the public internet, since that is where attackers have been getting in.

5

How it unfolded

  1. October 17

    Amazon sees the first exploit attempt against its honeypots, four days before the fix.

  2. October 20

    Details leak on Hacker News two days early. The PHP team posts an advance notice of an emergency release.

  3. October 21

    PHP ships fixes for 8.5, 8.4, 8.3 and 8.2. F5 Labs records thousands of exploit attempts within hours.

  4. October 23

    PHP flags a third, separate issue (CVE-2026-115560) that the October 21 releases do not fix. Its advice is to keep session upload progress switched off.

  5. October 23 to 24

    Security firm Dream reports that attackers chained PHP2Shell with a Linux kernel bug called Fragnesia (CVE-2026-46300) to get root on 24 Palo Alto Networks firewalls through their management interface. Palo Alto's Unit 42 verified the tooling.

  6. October 26

    CISA adds both PHP2Shell CVEs to its Known Exploited Vulnerabilities catalog.

  7. November 3

    Singapore's Cyber Security Agency warns that attackers are hitting the management interfaces of network and security products, and names Palo Alto, Cisco, Citrix, F5 and Siemens among the affected vendors.

  8. November 12

    Check Point reports that attackers chained PHP2Shell with a second bug to get root on its gateways, in attacks between October 30 and November 4.

Reality check: most traffic is still scanning and failed attempts. Wiz found that a working attack has to be tuned to each server's PHP build and memory layout, and Fastly found that other campaigns were being counted under PHP2Shell signatures. The confirmed break-ins are real, though, and they cluster on setups that were easy to reach. Scale: Mallory counted about 2.6 million internet-facing services showing a PHP version, and roughly 73.5% ran PHP 8.1 or older. Wiz measured about 67% fewer exposed vulnerable machines in the first week. Figures last checked on November 13, 2026.
